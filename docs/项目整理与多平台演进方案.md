# 项目整理与多平台演进方案

日期：2026-09-14。检查基线：`ec97a7e` / `0.4.24`。

性质：基于现有代码的整理建议，尚未实施目录重构或迁移到 GitHub。
已确认方向：先建立私有协作仓库，整理完成后再公开。

## 1. 推荐路线

以现有 `commercial_draft_tool` 独立工程为仓库根目录，先完成交接和可重复验证，再逐步发展为多平台商品采集与草稿管理工具。保留单仓库、单 Python 工程；第二个平台形成可运行流程后，再确定需要共用的模块接口。当前没有证据支持立即拆微服务或建立独立插件市场。

把整理分成三个可验收阶段：能交接 → 能协作 → 能扩展。首次私有协作不必等待全部多平台架构完成。

## 4. 多平台按来源和目标分别扩展

建议的数据流：

```text
1688 / 抖音 / 拼多多采集模块
              ↓
       源商品快照与来源证据
              ↓
       统一商品数据与素材引用
              ↓
  目标平台 + 店铺 + 类目规则转换
              ↓
    目标草稿计划与不兼容项清单
              ↓
   目标平台适配器：填充 → 保存 → 重开核验
              ↓
      执行报告、草稿台账、人工处理
```

采集模块不需要知道未来上传哪个店铺；目标适配器不重新解释其他平台的原始 HTML。只有“源解析 → 统一商品”和“统一商品 → 目标计划”两处需要转换，避免逐对开发 1688→抖音、抖音→拼多多等完整流水线。

同时保留平台特有信息：统一模型表达共同含义，平台扩展字段和来源证据保留原始差异。不能为了字段统一，丢掉价格条件、SKU 区别或媒体归属。

建议的最终目录形态如下，属于渐进目标，不要求一次搬迁：

```text
src/draft_tool/
  domain/                    # 商品、SKU、媒体、目标计划和结果约定
  application/               # 采集、校验、草稿任务的编排
  platforms/
    alibaba1688/              # 采集、类目规则、页面控制、上传回执
    douyin/                   # 有真实实现后建立
    pinduoduo/                # 有真实实现后建立
  infrastructure/            # 文件存储、SQLite、浏览器会话、下载机制
  interfaces/                # CLI 和桌面启动器
tests/
  unit/
  contracts/
  browser/
  fixtures/
```

核心商品规则不导入具体平台页面模块或 DrissionPage。网页选择器、跨域选图器、回执格式、平台登录识别由平台适配器维护；共用基础机制通过少量接口提供。不要建立一个要求所有平台都实现所有字段的巨型基类。

短期保留包名 `draft_tool`、已有 CLI 入口和运行数据目录。仓库可以使用更通用的名称，但名称变化和存量用户迁移应分开处理。

## 5. 第二个平台前必须明确的数据约定

| 主题 | 现有约定或风险 | 建议约定 |
| --- | --- | --- |
| 商品身份 | 多处只使用 `offer_id`；采集输出目录也只按该值组织 | `(source_platform, source_product_id)`；ID 始终按字符串处理 |
| 目标身份 | 台账用店铺可见文字和源 offer ID | 稳定的目标平台/店铺 ID；可见文字作为登录核验信息，不能视为全局 ID |
| 草稿幂等 | 同平台场景键为 `(store_identity, source_offer_id)` | 初期定义每个来源商品在每个目标店铺最多一个受管草稿，键加入目标平台、店铺、来源平台和商品 ID；以后若允许多版本草稿，再引入独立方案 ID |
| 类目 | 未显式指定目标类目时回退源类目 | 同平台可保留已验证逻辑；跨平台必须显式映射，缺失时要求选择 |
| 商品属性 | 标签匹配可服务于当前页面 | 转换记录源属性、目标属性、单位和依据；相似名称不自动等同 |
| 价格 | 目前存在数字主价格、观察值和起批信息 | 明确币种、金额精度、阶梯价、起订量、条件；目标售价由显式规则产生，不能直接把采购价当零售价 |
| 库存 | 采集的是当时源库存观察值 | 保留采集时间和来源；目标可售库存独立设置，不能承诺实时同步 |
| SKU | 已有完整规格和媒体归属约定 | 保留完整维度、单位、源 SKU 身份与目标行映射；无法表达的组合返回不支持 |
| 图片与视频 | 已有内容 SHA256、媒体角色、平台回执 | 内容身份和平台媒体 ID 分离；同一图片在不同店铺的上传状态分别记录 |
| 配置 | 当前 target 不含平台、规则按类目 ID | 配置带版本；按目标平台、店铺、类目区分；采集端和目标端会话分离 |
| 数据版本 | product 有 `schema_version: 1.0`；media manifest 有独立版本 | 商品、媒体、配置、台账分别迁移；旧字段有兼容期，未知新版本明确拒绝 |

兼容 ADR 0002：`assets`、`detail_assets` 等旧字段不能在第一次整理时直接删除。迁移测试需用旧版商品样例确认 SKU、媒体引用和身份没有变化。

台账迁移先备份并核验。旧记录中的来源可按已知 1688 约定迁移，但店铺可见文字与稳定店铺身份不应自动猜测匹配。迁移不成功时停止写入目标平台，不重新创建一份可能重复的草稿。

## 6. 平台能力和执行结果

分别声明采集、媒体下载、草稿预览、草稿保存、重开核验、正式发布能力；再细化多维 SKU、SKU 图片、阶梯价、视频等。支持与否可以受类目和页面模式限制。

当前初始能力矩阵：

| 平台 | 商品采集 | 预览填充/草稿保存 | 正式发布 |
| --- | --- | --- | --- |
| 1688 | 已实现，支持范围需记录 | 已实现，0.4.24 为测试版，真实页面验收范围待补齐 | 程序禁止，人工完成 |
| 抖音 | 规划，尚未实现 | 规划，尚未实现 | 待另行设计 |
| 拼多多 | 规划，尚未实现 | 规划，尚未实现 | 待另行设计 |

“填充完成”“草稿保存成功”“重开核验通过”“商品已发布”必须是不同结果。后续真正实现自动上架时，单独设计发布接口、授权方式和验证证据，不能通过删除现有发布保护来实现。

任务结果应包含阶段、已确认操作、失败原因、是否可能已经产生副作用、是否允许重试及证据位置。复用现有 Indeterminate Upload 约定：结果未知时不能作为普通网络失败重新上传或重新保存。

接入抖音/拼多多前，逐个平台核实可用访问方式、授权条件、所需字段和目标能力；本方案没有验证这些平台当前支持的接口，也不承诺其页面流程与 1688 一致。

## 7. GitHub 协作和维护规则

建议采用 `main` 加短期功能/修复分支；每个 PR 关联问题和验收条件。由总维护者把握范围、数据兼容与发布，由平台维护者负责自己的适配器和验收。小团队可一人兼任多个角色，随后用 CODEOWNERS 记录实际人员。

Issue 模板至少包括故障报告和平台/功能提案。故障报告收集版本、Windows/浏览器版本、源与目标平台、类目、失败阶段、最小复现及脱敏报告；不要求贡献者上传完整 Profile 或原始账户页面。

GitHub 支持 CONTRIBUTING、行为准则和 Issue/PR 模板，可把这些入口放入仓库，让新参与者直接找到协作要求。[社区文件说明](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file) [Issue 模板说明](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/configuring-issue-templates-for-your-repository)

任务迁移时建议只把当前未完成任务放入 GitHub Issues，历史 `.scratch` 保留链接。迁移完成后，以 GitHub Issue 为任务状态唯一来源；Markdown 规格、ADR 和验证证据仍随代码版本管理。同步修改现有 `docs/agents/issue-tracker.md`，避免人和代理维护两份不同状态。

每个改动的完成条件：

1. 有可理解的问题、预期行为和适用平台。
2. 缺陷有能复现原失败的回归；涉及网页切换时保留实际浏览器行为，如跨域 iframe。
3. 公共数据约定变化附兼容策略与样例。
4. 说明测试范围、真实页面验证范围和剩余限制。
5. 新支持能力同步更新能力矩阵；部署或升级变化同步更新用户文档。

平台页面变动时，先用脱敏证据定位失败阶段，在受影响平台内修复；不为单个平台故障修改公共语义。相同 URL 或选择器变化不意味着需要重新设计整个商品模型。

## 8. 测试和发布需要移交给仓库

基线验证记录为 2026-09-11 的 175 项通过（含 56 项隔离 Chrome 测试），本次分析未重跑这些测试。

建议三层验证：

| 层次 | 触发方式 | 验证内容 |
| --- | --- | --- |
| 数据与契约测试 | 每个 PR | 解析、商品/SKU/媒体规则、旧数据兼容、跨平台身份冲突、目标转换 |
| 隔离浏览器测试 | 涉及页面操作的 PR，至少合并前 | 临时 Profile、合成页面、跨域/弹框/上传回执/重开等状态 |
| 真实平台验收 | 平台功能发布前，由授权维护者执行 | 记录平台、类目、页面模式、版本和日期，核对实际可见结果 |

先在 Windows CI 建立与当前开发环境一致的验证，再决定是否支持其他系统。现有锁机制使用 `msvcrt`，不能只根据 Python 安装成功就声明跨平台可运行。

公开贡献的 PR 在不携带真实账号或发布凭据的临时 runner 上测试。真实店铺验收放在独立受控环境；不要用登录了店铺的个人电脑作为公共 PR runner。[GitHub Actions 安全说明](https://docs.github.com/en/actions/reference/security/secure-use)

首批发布工程任务：

- 将 `.local/verify_release_0_4_24.py` 的通用逻辑参数化并纳入 `scripts/verify_release.py`，自动验证版本、包内容、CRC、哈希、烟雾启动。
- 为经过验证的运行和打包依赖建立约束/锁定文件，记录 Python、DrissionPage、Chrome 和 PyInstaller 版本。保留依赖升级验证流程。
- 修正测试/安装脚本的失败传播；统一版本来源，或在 CI 检查 VERSION、包元数据、运行版本一致。
- 调整构建时复制整个 `docs` 的做法，明确面向用户的打包文档清单，避免以后把内部交接分析全打入 EXE。
- 从固定提交构建，测试完成后生成发布清单；发布后的同版本包不覆盖，内容变化使用新版本。
- Windows ZIP 和校验文件作为 GitHub Release 附件；源码仓库不跟踪 `dist`。

GitHub Releases 支持附加二进制文件及标记 pre-release，适合交付当前测试构建。[发布管理说明](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)

升级还需要覆盖用户数据：配置、商品数据和 SQLite 台账迁移前备份，说明能否回退；不能只保留旧 EXE 就认为可以回退到旧数据格式。

## 9. 按可交付结果拆分工作

| 顺序 | 工作包 | 依赖 | 验收条件 |
| --- | --- | --- | --- |
| A | 发布范围与历史审查 | 无 | 明确仓库根、待推送分支/标签、许可决策清单；运行数据不在交付内容中 |
| B | 新人交接文档与合成样例 | A | 新协作者能从干净克隆安装、运行离线校验、理解失败报告并找到对应代码 |
| C | CI 与可复现发布 | B | 测试失败使 CI 失败；无真实账户可跑自动验证；包验证脚本来自仓库 |
| D | 私有 GitHub 协作 | A、B；C 随后设为合并要求 | 至少一名协作者按文档完成小型 PR；实际角色与 Issue 流程生效 |
| E | 1688 模块提取与旧数据兼容 | C、D | 现有 CLI/GUI/数据仍可用；行为回归通过；真实页面范围有记录 |
| F | 第二来源平台的一条完整流程 | E、商品约定决策 | 二选一接入抖音或拼多多采集，生成统一商品，经显式类目/价格转换进入已验收的 1688 草稿流程 |
| G | 第二目标平台与公开协作 | 对应适配器和公开条件完成 | 目标能力明确、端到端验收有证据；公开前复查历史、许可、模板、报告脱敏与支持范围 |

第二目标平台和公开仓库不必互相等待：满足公开条件即可开放贡献，不必等三平台功能全部完成。后续每增加一个来源或目标，先交付一条小范围完整流程，再扩大类目和功能覆盖。

不要把“抖音/拼多多采集全部完成”“所有平台自动上架”写成单个大任务。建议下一轮规格先聚焦 A–D，架构重构和新平台接入各自独立立项。

## 10. 仍需由项目所有者决定的事项

- GitHub 仓库归属个人还是组织，仓库名称，以及维护者名单。
- 公开时采用何种使用与分发授权；私有协作期间的授权安排。
- 第二个平台优先接抖音还是拼多多；先增加来源采集还是目标草稿能力。本方案推荐先增加一个来源，利用现有 1688 目标验证商品约定。
- 是否把正式自动发布纳入未来范围；当前草稿功能的承诺不因此扩大。

按 `$ask-matt` 的路线，现阶段已完成现状分析；接下来适合把首批整理范围写成规格并拆成有依赖的任务，再逐项实现。无需先做全量重构，协作者就能开始参与文档、回归样例和明确的小型修复。
